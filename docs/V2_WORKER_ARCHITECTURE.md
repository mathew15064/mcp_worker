# mcp_worker v2 — Outbound Worker Architecture

## Goal

mcp_worker v2 removes the requirement for inbound SSH access to managed machines.

The control server keeps the existing MCP reasoning/execution surface, but execution happens through a lightweight worker running on the user's machine. The worker opens an outbound TLS/WebSocket connection to mcp_worker and receives typed jobs over that authenticated connection.

```text
ChatGPT / MCP client
        |
        v
mcp_worker v2 server
        |
        | authenticated job/event over WSS
        v
Worker (outbound connection only)
        |
        +-- local tmux
        +-- local files
        +-- local git
        +-- local processes
        +-- local checks
```

## Security properties

- No inbound SSH port is required on the worker machine.
- mcp_worker does not store SSH usernames/passwords for worker targets.
- The worker generates an Ed25519 key pair locally. The private key never leaves the worker machine.
- Enrollment uses a short-lived one-time token generated by an administrator.
- After enrollment, WebSocket handshakes are authenticated with a signed timestamp + nonce challenge using the worker private key.
- Replay protection is enforced with timestamp skew limits and one-time nonces.
- The server stores only the worker public key and metadata.
- An administrator can disable a worker identity. Disabled identities are rejected during future handshakes/dispatch and an active connection is terminated.
- The worker runs as a normal OS user; commands execute with that user's permissions unless the worker host itself explicitly grants passwordless sudo.
- Local worker policy is authoritative for allowed workspace roots and optional shell execution. The server cannot widen that policy remotely.
- Job payloads are typed and bounded. Results are correlated by `job_id` and returned only on the authenticated worker connection.

## Compatibility strategy

v2 introduces workers without deleting v1 SSH support immediately.

Execution profiles have a transport:

- `ssh` — existing v1 Terminal Profile behavior.
- `worker` — new outbound worker transport.

The 19 MCP tool names remain stable. A profile alias determines which transport executes the request. This allows a machine to migrate from SSH to worker without changing ChatGPT-side tool usage.

The intended v2 default is `worker`. SSH remains a compatibility path only and can be removed after worker migration is complete.

## Worker lifecycle

1. Admin creates a short-lived one-time enrollment token.
2. User installs the standalone CLI with the platform-specific installer: Linux `/worker/install-linux.sh`, macOS `/worker/install-macos.sh`, or Windows PowerShell `/worker/install.ps1`. Each installer verifies the downloaded binary against server-published SHA-256 sums; no language runtime is installed on the target.
3. User runs `bot-report-worker login`; the CLI reads the one-time token with hidden input, selects local allowed roots and the explicit shell-execution policy.
4. CLI creates an Ed25519 key pair locally and POSTs only its public key to `/worker/v1/enroll`.
5. mcp_worker validates and consumes the token, creates the worker identity and a unique Worker Profile alias, and returns both identifiers.
6. CLI stores config, `worker_id`, and the private key locally with restrictive permissions. The one-time token is not persisted.
7. CLI starts the worker in the background; interactive PTY shells are created on demand per profile rather than pre-creating a tmux session.
8. Worker opens outbound `wss://.../worker/v1/connect` with signed authentication headers. `login` waits for this connection before reporting success.
9. Server marks the worker online and can immediately dispatch jobs through the auto-created profile alias.
10. Worker sends heartbeat frames, including its current capability set; server updates `last_seen_at` and capability state. MCP execution is converted into typed worker jobs and returned over the authenticated connection.

## Initial typed operations

The worker transport exposes the same low-level execution capabilities needed by the current MCP service:

- `shell.inspect`
- `shell.send`
- `shell.read`
- `shell.interrupt`
- `shell.attach` (streaming PTY for browser Attach Shell)
- `workspace.exec`
- `artifact.collect`
- `file.write`
- `process.start`
- `process.status`
- `process.logs`
- `process.stop`

Higher-level MCP tools such as `repo_snapshot`, `git_diff`, `code_search`, and `check_run` continue to compose these primitives server-side, preserving the current tool contract.

## Failure behavior

- Offline worker: fail immediately with `WORKER_OFFLINE`; v2 does not silently queue arbitrary remote-code jobs for later execution.
- Authentication failure: reject WebSocket upgrade.
- Expired enrollment token: enrollment fails closed.
- Duplicate/replayed handshake nonce: connection fails closed.
- Job timeout: server returns `WORKER_JOB_TIMEOUT`; worker may continue local cleanup but the server no longer accepts the late result as active request output.
- Worker disconnect: all pending jobs for that worker fail immediately.

This fail-fast model is intentional. It is safer and easier to reason about than a durable remote-code queue.

## Local policy

The installed CLI persists local policy under `~/.bot-report-worker/config.json`; machine identity/private key live in `~/.bot-report-worker/state.json`. Both are local files and the mcp_worker server cannot widen their policy remotely. Equivalent environment variables remain supported for compatibility and test/runtime overrides:

```text
BOT_REPORT_WORKER_SERVER_URL=https://bot-report.example.com
BOT_REPORT_WORKER_ALLOW_INSECURE_HTTP=false
BOT_REPORT_WORKER_STATE_PATH=~/.bot-report-worker/state.json
BOT_REPORT_WORKER_ALLOWED_ROOTS=/home/user/work,/srv/projects
BOT_REPORT_WORKER_ALLOW_SHELL=true
BOT_REPORT_WORKER_MAX_JOB_MS=300000
```

All path-bearing jobs must resolve inside an allowed root. When shell execution is disabled, `workspace.exec`, checks, git helpers, and managed processes are rejected locally. Allowed roots are a path-policy boundary, not a shell sandbox: once shell execution is enabled, a command has the normal filesystem/process authority of the OS user running the worker. Use a dedicated low-privilege account or an external OS/container sandbox when stronger isolation is required.

## v2 implementation phases

### Phase 1 — transport foundation

- worker identity/enrollment tables
- outbound authenticated WebSocket broker
- worker client process
- job correlation + heartbeat
- typed worker execution service
- unit/integration tests

### Phase 2 — execution profile integration

- Worker-backed SSH Profiles in Admin/User UI
- bind a profile alias directly to a Worker identity
- provide persistent PTY shell operations and browser Attach Shell without tmux
- route the existing 19 MCP tools through worker transport
- preserve legacy direct-SSH data only as migration compatibility, not active execution

### Phase 3 — SSH deprecation

- migrate remaining profiles
- remove stored SSH password requirement for worker targets
- make worker the default profile type
- optional removal of SSH transport in a later major release
