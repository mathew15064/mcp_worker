## What a first-time owner should see **after** release + template approval

1. From the future **real**, owner-approved Railway template, choose **Deploy**
   and review **billing / storage / region**, granting explicit consent. The
   template must show **one Node app**, **one 512 MB SQLite volume** attached
   at `/app/data`, **one replica**, Dockerfile `Dockerfile.railway`, and no
   Redis/MySQL/Postgres/Neon/extra service. **No deploy link exists yet.**
2. Enter only the required private variable `MCP_SETUP_SECRET`. Generate
   32 bytes from a cryptographic RNG and encode using base64url (43 chars);
   safely save the original in your own password manager **outside** Railway.
   This value has **no default** in the candidate. Never put it in URL,
   source code, logs, template defaults or chats. Do not replace it casually:
   losing it can invalidate sessions and encrypted settings.
3. On the real Railway service, use **Settings → Networking → Public
   Networking → Generate Domain** and confirm actual HTTPS/TLS. Open
   `https://YOUR-VERIFIED-DOMAIN/setup`, supply the saved setup secret, set a
   distinct strong admin password, and complete admin claim. Configure OAuth
   PKCE and ChatGPT only after callback/origin inspection. Signed Worker
   enrollment is blocked until a separately approved signed release exists.

Railway may require domain generation **after** the first deploy; users may
need to redeploy/stage changes after editing variables. There is no automatic
DNS ownership verification for custom domains, billing consent, owner secret
custody, signed Worker trust, external backup setup, or ChatGPT OAuth approval.

The structured contract is `/.railway/template-candidate.json` in this
repository (relative path `.railway/template-candidate.json`). Railway does
**not** automatically import this JSON or turn the SDK IaC into a published
template. After independent release approval, the owner/operator must use
Railway's **Create a Template** composer:

| Composer field | Required value |
|---|---|
| Source | GitHub `mathew15064/mcp_worker`, **owner-approved protected** `release/*` branch URL, only after remote Actions disablement verification |
| Service | `mcp-worker`; Node application; **one replica** |
| Build | Custom Dockerfile `Dockerfile.railway` via `RAILWAY_DOCKERFILE_PATH` |
| HTTP | Listen internally on `0.0.0.0:80`; healthcheck `/healthz` and timeout 120 seconds |
| SQLite volume | **One** `sqlite-data`, 512 MB, region `us-west2`, attached at `/app/data` |
| Database | `DATABASE_PATH=/app/data/bot_report.sqlite` |
| Fixed runtime vars | `NODE_ENV=production`, `MCP_PLATFORM=railway`, `HOST=0.0.0.0`, `PORT=80`, `ADMIN_USERNAME=admin` |
| Fixed Railway vars | `RAILWAY_DOCKERFILE_PATH=Dockerfile.railway`, `RAILWAY_RUN_UID=0`, `RAILWAY_DEPLOYMENT_OVERLAP_SECONDS=0` |
| Required private input | `MCP_SETUP_SECRET`, no default, describe 32 random bytes base64url; only one owner-provided app setting |
| Platform-generated vars | `RAILWAY_VOLUME_NAME`, `RAILWAY_VOLUME_MOUNT_PATH`, `RAILWAY_PUBLIC_DOMAIN`; **do not fake** |
| Networking | HTTP Public Networking enabled or generated by owner, verified unique HTTPS domain; no hostname assumed |

`/healthz` is the pre-setup deployment liveness check (HTTP 200 once
running). `/readyz` deliberately returns HTTP 503 until owner setup and
canonical public origin are established; do **not** make it the initial
Railway healthcheck. A fake `RAILWAY_VOLUME_*` variable never makes an
ephemeral directory safe. Init runs as root because Railway volumes may be
root-owned; the application must drop to UID 1000.

### Safe source pin workflow

The local SDK graph currently uses a **zero SHA** and a deliberately
nonexistent `release/OWNER_APPROVAL_REQUIRED` branch. It blocks all
evaluation contexts except offline `plan`. These values are placeholders,
**not** an approved GitHub source.

Before release, the repository owner must **verify GitHub Actions disabled
remotely before pushing**; separately approve an entire, immutable release
commit; place it at a protected, dedicated release branch; check the branch
tip matches its full SHA and no force-push; review a separately gated IaC
change. Run `bash .railway/verify-release-pin.sh FULL_SHA release/VERSION`
against refreshed *local* origin refs; this script checks only cached refs.
Independently confirm real remote reachability and live deployed commit
against the approved pin. Railway's Template Composer points to a branch
URL, so branch drift remains a risk and cannot be eliminated by the local
SDK's `commitSha` alone.

## Local PC acceptance (repeatable, zero cloud side effects)

```sh
npm ci --prefix .railway
.railway/node_modules/.bin/tsx .railway/validate.ts
npm ci
npm run build
node --test dist/tests/railway-platform-config.test.js dist/tests/railway-platform-config-docker.test.js
docker build -f Dockerfile.railway -t mcp-worker-t3-local:verified .
bash scripts/test-railway-local.sh mcp-worker-t3-local:verified
RAILWAY_DOCKER_INTEGRATION=1 RAILWAY_TEST_IMAGE=mcp-worker-t3-local:verified \
  node --test dist/tests/railway-platform-config-docker.test.js
```

This verifies the real `railway@3.12.0` offline graph, template candidate
consistency, Docker build, 1 mounted SQLite volume, UID 1000, health and
pre-setup readiness, restart persistence + `PRAGMA quick_check`; rejects
missing/fake/readonly mount, wrong database path, weak/unset secret, SQLite
symlinks and incorrect user. All Docker resources are disposable and uniquely
named. No Railway CLI `apply`, publication, GitHub Actions or cloud spend.

## Live sign-off checklist — owner actions, NOT performed in T3

1. Owner separately approves billing/budget, test project, region, volume,
   explicit immutable release SHA, and any eventual template publication.
2. After GitHub Actions disablement is confirmed remotely, owner approves the
   source push and verifies the protected release ref/commit on GitHub.
3. Owner configures the real template and inspects every staged setting.
   Do not publish before approval; after authorization conduct a private
   disposable Railway test deployment.
4. In the live service, inspect source SHA, 1 service/replica/volume, correct
   Dockerfile/path, no external DB, UID 1000 and real writable volume. Confirm
   SQLite data survives a redeploy/restart with actual volume attached.
5. Generate a **real** domain; inspect HTTPS certificate/hostname, /healthz 200,
   pre-claim /readyz 503, /setup accessibility. Claim owner; confirm readiness,
   OAuth PKCE canonical redirect URLs, verified ChatGPT authenticated
   read-only `runtime_info`, and Worker WSS only if separately signed/approved.
6. Verify encrypted off-platform backup, key custody and **independent** restore
   before any production-data claims. Review restart/downtime with single
   volume/replica and consent for operational costs.
7. After separate publication consent, publish the genuine template and record
   its **real** URL. Pilot a new account's full Deploy→owner claim flow; do
   not claim success from mock domains or local Docker alone.
