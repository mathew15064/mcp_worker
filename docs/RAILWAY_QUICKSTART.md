## Desired owner experience after release approval

1. Select **Deploy on Railway** from the future owner-approved Template and
   confirm Railway's service + persistent volume pricing. The Template must
   create **one application**, **one SQLite volume** mounted at `/app/data`,
   **one replica** and use `Dockerfile.railway`. No managed database/cache.
   There is **no published button/link yet**.
2. Enter **one required private variable**: `MCP_SETUP_SECRET`. Generate a
   unique random **32-byte base64url** secret in your password manager, retain
   the **original value** safely outside Railway and paste it into the Railway
   service's private variables. It is not generated by this IaC, and
   `preserve()` means **keep existing value**, not **make a secret**.
   Never commit it, send it in a URL, or put it in Template defaults.
3. In Railway **Public Networking**, choose **Generate Domain** and verify
   the public HTTPS URL (or configure verified custom TLS/DNS separately).
   Then open `https://YOUR-DOMAIN/setup`, enter the saved setup secret and
   choose a **different** admin password of at least 14 characters. Finish
   admin setup, create an OAuth/PKCE client and, after signing approval,
   enroll a verified Worker. **Do not hand-enter the routine variables below.**

## Preconfigured by the candidate IaC

| Setting | Value |
|---|---|
| App / replica | `mcp-worker` / exactly 1 |
| Persistent SQLite | `sqlite-data` -> `/app/data/bot_report.sqlite` |
| Runtime | `MCP_PLATFORM=railway`, `NODE_ENV=production` |
| Internal network | `HOST=0.0.0.0`, `PORT=80`, Docker health `/healthz` |
| Image build | `RAILWAY_DOCKERFILE_PATH=Dockerfile.railway` |
| Volume initializer | `RAILWAY_RUN_UID=0` only for entrypoint; Node runs as UID 1000 |
| Volume overlap | `RAILWAY_DEPLOYMENT_OVERLAP_SECONDS=0` |
| App restart | on failure, up to 10 retries |

Railway's generated `RAILWAY_VOLUME_NAME`, `RAILWAY_VOLUME_MOUNT_PATH`
and `RAILWAY_PUBLIC_DOMAIN` must be supplied by the platform at runtime.
A fake volume env variable **does not** satisfy the real mount check.
An unset/weak `MCP_SETUP_SECRET` fails startup; changing the original secret
later may invalidate sessions and make encrypted settings unreadable.
If the original is lost, there is no guaranteed recovery of that data.

**Endpoint meanings:** `/healthz` is process liveness and is the correct
pre-setup deployment healthcheck. `/readyz` returns HTTP 503 until persistent
SQLite, a canonical public origin and owner setup are complete. It must not
be configured as the initial Railway healthcheck. `/setup` is for the owner's
first claim. Public HTTPS is provided by Railway networking, not by the
container listening with local TLS.

## Local maintainer verification (PC only)

Run from the checkout; Docker 29 and Node 22 are available on the PC:

```sh
npm ci --prefix .railway
./.railway/node_modules/.bin/tsx .railway/validate.ts
./scripts/test-railway-local.sh
```

The last command builds `Dockerfile.railway` **locally** and uses a fresh,
task-namespaced disposable Docker volume/container. It probes `/healthz`,
`/readyz`, `/setup`, verifies UID 1000, inserts/checks a persistent SQLite
marker and `PRAGMA quick_check` across restart, and rejects missing/forged/
read-only mounts, unsafe SQLite symlinks and missing/weak setup secrets.
It removes **only its own** disposable container and volume. It does **not**
contact Railway or publish anything. The SDK test validates a **local graph**,
not a linked `railway config plan`. No GitHub Actions or CI/CD are required.
